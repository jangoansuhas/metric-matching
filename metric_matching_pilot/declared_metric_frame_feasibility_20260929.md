# Declared-metric frame: metadata-only feasibility

**Date:** 2026-09-29  
**Decision:** A separate public dbt Semantic Layer discovery frame is plausible enough to specify, but this pass establishes **zero eligible repositories**. Six distinct analytics-project leads appear below. Their declared-metric counts, exact licenses and independence remain unverified. This is a lead list, not a cohort, a prevalence estimate, or a metric-pair evaluation.

## Boundary and evidence

This pass used public GitHub repository titles, descriptions, topics, license indications in GitHub search listings, the [GitHub repository-search documentation](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories), [dbt's metric documentation](https://docs.getdbt.com/docs/build/build-metrics-intro), and the [dbt Package Hub](https://hub.getdbt.com/) as a check on package-oriented discovery. Search-engine indexing of official GitHub listing pages helped locate the leads; it is **not** a reproducible GitHub API census. No candidate repository source file, README, YAML, manifest, or license text was opened; no repository was cloned; no metric-pair outcomes or values were consulted. Incidental source snippets returned by public search were not used to infer counts or eligibility.

GitHub repository search normally searches **name, description and topics** unless `in:readme` is requested. It cannot search arbitrary repository contents or return the number of dbt declarations. dbt defines metrics in project YAML, with a changed YAML layout in newer versions; an analytics description or a license indication cannot establish five valid, distinct, enabled declarations. [GitHub search fields](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories) · [dbt metric concepts](https://docs.getdbt.com/docs/build/about-metricflow) · [dbt migration guide](https://docs.getdbt.com/docs/build/build-metrics-intro)

## Reproducible search and ranking rule for a new frame

Run each query twice, replacing `LICENSE` with `mit` and `apache-2.0` initially. Add other [OSI-approved SPDX IDs](https://opensource.org/licenses) by an enumerated rule in the new protocol. These queries intentionally omit `in:readme` and code search.

| Repository-search `q` (URL-encode for the API) | Purpose |
| --- | --- |
| `"dbt semantic layer" in:name,description,topics is:public archived:false template:false mirror:false license:LICENSE` | High-specificity self-description. |
| `metricflow in:name,description,topics is:public archived:false template:false mirror:false license:LICENSE` | Alternate official engine name. |
| `topic:dbt topic:semantic-layer is:public archived:false template:false mirror:false license:LICENSE` | Topic intersection; optional/owner-assigned and therefore incomplete. |
| `dbt metrics in:name,description,topics is:public archived:false template:false mirror:false license:LICENSE` | Broader recall, with more false positives. |

Use `GET https://api.github.com/search/repositories?q=<encoded-query>&per_page=100&page=1` and preserve each page, query, timestamp, `total_count`, `incomplete_results`, pagination and API version. For every distinct repository ID record `full_name`, `html_url`, description, topics, visibility, `fork`, `archived`, `is_template`, `mirror_url`, `license.spdx_id`, `default_branch`, `pushed_at`, and the eventual pinned commit separately. Default repository search excludes forks unless `fork:true`/`fork:only` is added; still check the returned `fork` field. Keep separate query strata and deduplicate by repository ID before ordering. [Repository qualifiers](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories) · [REST search endpoint and response](https://docs.github.com/en/rest/search/search#search-repositories)

**Prospective ranking, before source access:** (1) require a public, distinct, non-fork repository with a recognized OSI-approved license *indication* and no archive/template/mirror flag; (2) rank explicit dbt Semantic Layer or MetricFlow descriptions above generic dbt/“semantic layer” descriptions; (3) rank domain analytics projects above libraries, agents, CLI tools, connectors, packages, tutorials, workshops and dbt vendor examples; (4) prefer descriptions naming multiple analytical domains or KPI marts over single-metric demonstrations; (5) use stable repository ID as the tie-breaker, and cap correlated owners or shared datasets according to a predeclared independence rule. Do not sort by stars, apparent metric names, source snippets, or promising pair examples. Hash selection from the frozen eligible metadata frame, plus an exclusion ledger, is preferable to manually taking these six in rank order for a held-out study.

Examples to **exclude from this non-development stratum** on their public descriptions are [dbt-labs/metricflow](https://github.com/dbt-labs/metricflow) (engine), [dbt-labs/jaffle-sl-template](https://github.com/dbt-labs/jaffle-sl-template) (template), and [fivetran/dbt_ad_reporting](https://github.com/fivetran/dbt_ad_reporting) (reusable dbt package). The [dbt Package Hub](https://hub.getdbt.com/) is useful for finding packages, but it is not a registry of independent analytics projects with counts of declared metrics. These exclusions are a proposed frame distinction, not a source-screen verdict.

## Search/API constraints and interpretation

- [GitHub REST search](https://docs.github.com/en/rest/search/search) exposes at most **1,000 results per query**, at most **100 per page**, and searches at most **4,000 repositories matching filters**. Partition a broad query by predeclared date or other metadata strata; deduplicate and retain every stratum's denominator. `total_count` is not an eligible-project count. Timeouts can set `incomplete_results=true`.
- Search has separate rate limits: GitHub documents **10 requests/minute unauthenticated** and **30/minute authenticated** for most search endpoints, with a separate code-search limit. Queries have a 256-character non-qualifier text limit and at most five Boolean operators. Authentication and access scope can affect returned results. Record the actual response and limits rather than assuming complete coverage. [GitHub REST search](https://docs.github.com/en/rest/search/search)
- GitHub's repository `license:` match and `license.spdx_id` are useful metadata filters; [MIT and Apache-2.0 are OSI-approved](https://opensource.org/licenses). Public visibility alone is not an open-source grant, and a repository-level detection does not settle file, dataset, third-party, dual-license, or redistribution rights. Confirm the governing license in the later, authorized source screen. [GitHub licensing guidance](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)
- This pass did **not** run the GitHub REST endpoint or measure result counts. Current candidate listing evidence comes from indexed official GitHub repository pages and can be stale. In particular, these six are leads for a fresh direct-API metadata capture, not the output of the four exact queries above.

## Coverage and selection risks; next gate

Repository words and topics favor authors who advertise MetricFlow; many dbt projects may omit that wording, avoid public GitHub, have no machine-detected license, or keep definitions in different locations. GitHub's best-match order and indexed page freshness are unstable. Vendor demos and training projects may dominate search hits, while filtering packages removes a potentially metric-rich but different population. An OSI-only, non-development, public-GitHub frame therefore estimates only that **restricted population**, not industrial prevalence. Forks, copied templates, common underlying datasets and correlated owners can make nominally distinct projects non-independent.

The `>=5` gate is especially fragile: a name or documentation claim may refer to measures, SQL columns, dashboards, generated variants, disabled definitions, legacy YAML, dependency-provided metrics, or another semantic layer. dbt's newer metric specification changes where declarations reside. Decide in advance whether five means unique enabled native dbt/MetricFlow metric nodes **owned by the pinned project**, how legacy definitions and parsing failures count, and whether the threshold is declaration-only or requires build/query support. Report every exposed definition and each denominator separately; do not silently drop unsupported cases. [dbt metrics overview](https://docs.getdbt.com/docs/build/build-metrics-intro) · [MetricFlow concepts](https://docs.getdbt.com/docs/build/about-metricflow)

**Stop here.** Before opening any of these candidate repositories' source, create and date a *new* Semantic Layer manifest/protocol: frozen query responses and candidate IDs, commit pinning, license and non-development rules, metric-count definition across dbt versions, independence and replacement rules, source-inspection budget, and hash-based selection. This frame is separate from the existing generic public-repository search manifest and source-screen amendment. Then perform an outcome-blind declaration/coverage screen at selected pinned commits, recording exclusions and failures. Pair sampling, human labels, method comparisons and claims of recall require their separate reviewer and evaluation gates. No source access or pair outcome is authorized by this feasibility memo itself.
