# Study object and substitution scope review — 29 September 2026

**Decision for the manuscript freeze.** Retain *identified numeric aggregate-query outputs* as a protocol-established eligibility route, but distinguish them from published MetricFlow metrics throughout the paper. The current outline is internally inconsistent if its two source-output-screened projects are counted as evidence for a method that requires compiled MetricFlow metric queries. Adopt a typed source-output frame and a generic SQL path before making a relationship-method comparison. Until that path has fixed, development-tested extraction and same-input baselines, the selected projects support only eligibility and extraction-coverage reporting. Do not silently reclassify source SQL as MetricFlow metrics or treat a failed MetricFlow compilation on a project with no MetricFlow declarations as a method failure.

**Review boundary.** This review uses `metric_matching_paper_outline.md` version 51 (29 September 2026), the existing selection/amendment protocol, and public development reports listed below. No held-out repository source, pair outcomes, labels, or metric values were opened for this review. The outline itself was not edited.

**Preferred route:** Keep the source-output eligibility decision and the selected-project order intact. Broaden the manuscript's object wording from MetricFlow-only declarations to typed, source-defined exposed outputs; fix the generic bridge on development material and disclose that it follows the already observed source-format screen. Apply a frozen bridge once for a complete per-project inventory, and compare methods only on pairs and query scopes where the same evidence is available. Report MetricFlow compilation coverage over the *MetricFlow-declaration denominator* and generic SQL compilation/trace coverage over its own denominator. If the authors instead want a specifically compiled-MetricFlow paper, the selected SQL-output projects are eligibility/coverage observations for the broader protocol, not a two-project test of that narrower method; a new, prospective MetricFlow-qualified sample and claim would be needed. Do not retrofit the screen or replace projects on the basis of method coverage.

## Freeze the target of “substitutability”

A definition is an interface, not just one observed number. For a versioned output `m`, let `F_m(q, D)` be the keyed numeric result, including key presence and `NULL`, for a supported request `q` and aligned pinned input/snapshot `D`. The request records time bounds and calendar/time zone, grouping grain and dimensions, filters/population, units, value/rounding policy, engine/adapter, and any declared transformation or alias mapping. Semantic equivalence at a target request concerns admissible inputs `D` under stated constraints; one finite execution can refute equality but cannot prove it generally. For a fixed SQL aggregate query, only its identified query and explicitly supported parameters/groupings belong to its request domain; underlying columns do not imply arbitrary groupability. A MetricFlow declaration may support a wider request domain, but that support and its generated SQL must be verified per relevant request.

Make each human and method output a **pair plus a declared target request or request family**. The label and evidence status apply to that target. Keep the frozen definition-ID and unordered-pair frame from §5; scope-specific judgments are attached to the pair and do not manufacture extra metric IDs or redraw pairs. Predeclare the compatible target requests before method outputs or labels. If no common valid request exists, report `no_common_request`/`needs_review` with the missing binding, rather than treating a syntactic difference as `non_match`. A general substitution assertion must state its supported domain; it is stronger than a single-request scalar decision.

| Target request | What can establish or refute substitution | Current development boundary |
| --- | --- | --- |
| Ungrouped scalar | Compare the same supported query request, population, input state, type/value policy and output mapping. Identical generated SQL modulo a cosmetic alias supports query-program identity for that request, conditional on the same engine and sources; finite equal totals alone do not prove it. | `revenue` and `cumulative_revenue` have the same ungrouped generated operation and both yielded $637,444 on the reconstructed Jaffle input. This is no ungrouped mismatch. `revenue_growth_mom` has no valid ungrouped query in the development build. |
| Time grouping and bounds | Compile and compare each relevant supported time request with aligned bounds/calendar, output keys, lookback, accumulation and period aggregation. One aligned unequal key refutes substitution for that request and any broader claim containing it. | In the bounded `metric_time__month` Jaffle run, October 2024 is $19,422 for `revenue` and $15,670 for `cumulative_revenue`; the two compiled month queries differed on all 12 observed month keys. The query used reconstructed public seed relations and a bounded spine, not a full dbt build. |
| Non-time dimensions and cross-grain rollup | Verify supported dimension paths, join cardinality/fanout, filters, additivity, key coverage, missing groups, `NULL`/zero, rounding and the specified rollup. Compare keyed results under the same request. | Ungrouped identity and the month witness say nothing by themselves about customer/product or other dimensions. Constructed day/order checks elsewhere in the development packet are not compiled MetricFlow proof at every grain. |

For `direct_equivalent`, require the same defined output at the **declared** compatible scope; for `cross_grain_equivalent`, require a specified valid transform and its prerequisites. Preserve the six existing taxonomy names and the separate `needs_review` axis. A universal claim over a request family needs support over that family, not a single compiled scalar; one valid counterexample can disprove the family claim, while finite agreement cannot prove it. Do not count an unsupported request as an inequality or silently fill missing groups with zero.

## The permissive AST example: exactly what was refuted

`aggressive_ast_equivalence_report.md` says its evidence is the **ungrouped** compiled SQL AST, normalized for aliases, but its emitted `direct_equivalent` means **general metric substitutability**. It asserted that for `cumulative_revenue`/`revenue` once in 171 Jaffle development pairs and abstained on 170. The independently compiled month request in `experiment_cumulative_revenue_report.md` is inside that *asserted general domain*, so the aligned October unequal values refute the **broad assertion on this bounded reconstruction**. They do **not** refute an assertion explicitly restricted to the identical ungrouped query. If the paper's primary target for that pair is only an ungrouped scalar, the month result must not be charged as an unsafe primary-scope assertion. State the assertion scope and evaluation scope on every baseline row before scoring.

This is a diagnostic against one deliberately permissive baseline rule, not a failure of AST comparison generally, a six-class gold label, or a held-out unsafe-assertion rate. The guarded mask-aware AST comparator produced the same two scope-variant outputs and 169 abstentions as the narrow proposed rule on the development packet; there is no observed incremental detector advantage. For §6's primary unsafe-equivalence measure, use only common decided pairs with a predeclared target scope and an independent adjudicated reference that rejects equivalence **at that scope**. Put contradicted broad assertions outside the primary target in a separate scope-extension diagnostic, and unknown prerequisites in the unsupported category.

## Paste-ready edits for the next outline revision

These are replacement passages; they are recommendations in this review, not changes to the outline or its frozen historical protocol.

### §2 — replace “Comparison unit” and add a scope rule

> **Study object and comparison unit.** An eligible object is one identified numeric output at a pinned public-project revision: either a semantic metric declaration or a reproducibly identified aggregate-query output projection. Record publication/consumer exposure as evidence, not an added eligibility gate. Retain the output kind and source ID, native request contract, and any verified declaration-to-measure/model or source-to-compiled-query binding. A measure, raw numeric column, or incidental unprojected aggregate is not an additional output. The comparison is one unordered output pair under a predeclared compatible request or request family, including grouping keys, grain, time bounds/calendar, population/filter, snapshot, units, missing-group and value/NULL rules. A grouped request returns keyed scalar values; whole-row equivalence beyond those keys and values is outside the task. Labels and missing prerequisites attach to the stated request scope. General substitutability across requests is a separate, explicitly bounded assertion.

Keep the class table and evidence axis, but add after them: “An unsupported or unverified shared request is `needs_review`/inapplicable for substitution, not a negative semantic label. Direct and cross-grain equivalence require source-supported prerequisites at the declared scope; an observed equal total is insufficient.”

### §4 — replace method items 1–3 and qualify item 5

> 1. **Inventory.** Enumerate all eligible numeric semantic metric declarations and reproducibly identified aggregate-query output projections at the pinned revision, with kind, native scope, stable source ID, unsupported/unknown status and extraction failures. Keep measures and possible duplicate bindings separate. Enumerate the full emitted output-ID and pair frame before method outcomes; report unknown true projection arity and do not multiply an ID by hypothetical runtime groupings.
>
> 2. **Provenance.** For a MetricFlow metric, verify declaration → measure/semantic model → generated metric query for each claimed request. For a SQL aggregate output, verify source output → query/model and, when available, the same-revision compiled SQL and field lineage. A compiled dbt model is not a compiled MetricFlow metric query; source SQL without a verified build remains source evidence. Record adapter/engine, invocation, revisions, hashes and missing links separately by object kind.
>
> 3. **Signature.** Record the identified output, exposure evidence and request support, source expression and lineage, native/target grain, time and dimension support, filters, state/snapshot, units, joins/additivity, key presence, `NULL`/zero and rounding, plus evidence status and immutable references.
>
> 5. **Decision.** State the exact target request or bounded request family for each prediction, with supporting source, a justified transform and prerequisite statuses. Abstain when binding, request support, additivity, joins, time behavior or value rules remain unknown. Distinguish request-scoped equality from general substitution.

### §5 — replace the “Held-out selection” and “Study frames” scope clauses

> **Selection and frames.** The fixed source screen admits at least two inspectable numeric outputs per selected project through either the declared-metric or aggregate-query route. The currently reported two- and three-output lower bounds are source-screen observations, not complete denominators or MetricFlow declarations. Before outcomes, freeze every eligible output ID, kind, supported native request, unsupported/unknown item and unordered within-project pair. Preserve the fixed project order, pair draw and reviewer gate. Record coverage separately for MetricFlow-query generation and generic SQL query/model tracing; a zero MetricFlow denominator is a format stratum, not 0% MetricFlow success. The generic bridge is developed after the eligibility/format screen and its later coverage must be described as post-screen compatibility evidence, not a wholly untouched extractor test.

Retain the remaining human-blinding, anchor-completeness and capacity text. Add a scope field to prediction-free annotation packets before labels; do not select a favorable grouping after seeing a method result or value.

### §6 — replace the I1 row and add scoring boundaries

> **Source context (I1).** Run source/AST/lineage and constraint-aware comparators and the proposed rule over the same frozen pair IDs, typed output cards, verified artifacts and declared target requests, recording feature availability per object kind. MetricFlow-generated query AST comparisons apply only when both relevant metric queries are verified. Generic SQL comparisons use the verified output-query evidence available to both methods; they do not substitute a compiled model for a missing MetricFlow query. The permissive ungrouped-AST rule reports its broader substitution assertion separately from its ungrouped evidence. Compare decisions at matched input and claim scope; report unsupported strata rather than pooling them into method errors.

> **Measures and denominators.** Report eligible and unknown output counts, complete emitted pair frames, verified expression/query coverage, no-common-request and abstention counts by project and object-kind pair. For adjudicated pairs, score a claimed equivalence as unsafe only when the reference rejects it at the predeclared target scope; separate unsupported prerequisites and out-of-scope broad-claim counterexamples. Report general-substitution probes over time/dimensions as a distinct diagnostic with their exact request domain. A method contest or superiority claim requires a fixed portable generic path, natural decisions from both sides at the same evidence budget, and the existing independent adjudication and analysis thresholds.

**Consistency check on adoption:** Update the paper-at-a-glance phrase “numeric metric declarations,” the §7 corpus-flow headings, and the author-note phrases “metric IDs”/“compiled provenance” to the typed output vocabulary when these replacements are applied. Preserve the historical protocol and development counts as historical records; do not rewrite them into generic-output coverage.
