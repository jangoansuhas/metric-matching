# Held-out repository search surface audit

**Audit date:** 2026-09-28 UTC. **Scope:** public GitHub repository and Git-ref metadata only. This audit follows `heldout_sampling_protocol.md` and `evaluation_contract.md`. No repository source, README, SQL/YAML, metric definition, or prospective label was opened.

## Decision

**GO for a later, committed acquisition of the predeclared bounded search frame:** the REST repository-search endpoint returned complete, ordered JSON `items` arrays for all three fixed page-one requests, and the public Git-ref endpoint returned a default-branch commit SHA in metadata-only probes. The bounded frame is **page 1 only**, at most 30 results per query; it is not all matches for the two dbt queries.

**NO-GO for declaring a real manifest frozen from this audit.** The requests below were exploratory. Their full response bytes and headers were not retained as manifest artifacts, and HEAD was checked for only a few probe repositories, not every result. The digests below cannot reconstruct the responses. No eligibility or project selection has occurred. No held-out code should be opened on the strength of this audit.

GitHub does not supply an atomic, historical search snapshot or a shared as-of timestamp for search results and branch refs. A future manifest can pin **the observed rank array and each observed SHA**, with individual server and local acquisition times; it cannot claim all observations were simultaneous or that later reruns retain the same ordering. If a single-instant frame is required, this surface is **NO-GO** for that stronger requirement. The search API documents best-match/default ranking and selectable `updated` sorting, pagination, up to 1,000 accessible search results, and `incomplete_results` for timeouts; none is an as-of facility ([search API](https://docs.github.com/en/rest/search/search)).

## Locked search requests and bound

Use `GET https://api.github.com/search/repositories` with `Accept: application/vnd.github+json` and the observed working `X-GitHub-Api-Version: 2022-11-28`. The `q` values below are the exact, unquoted strings predeclared in the existing study protocol and `heldout_search_precommit.json`. The actual form-encoded URLs used `+` for spaces:

| Exact `q` text | Exact request target |
| --- | --- |
| `dbt metric` | `/search/repositories?q=dbt+metric&sort=updated&order=desc&per_page=30&page=1` |
| `dbt semantic model` | `/search/repositories?q=dbt+semantic+model&sort=updated&order=desc&per_page=30&page=1` |
| `rill metrics` | `/search/repositories?q=rill+metrics&sort=updated&order=desc&per_page=30&page=1` |

The fixed bound is **one complete page per query, three pages total**. Do not follow `rel="next"` for the committed frame, change sort/page size, add a qualifier, or stop early based on promising results. Preserve each page's array order as ranks 1–30 (or 1–N when fewer than 30 are returned), including a repository that appears in multiple queries. Deduplicate by GitHub numeric repository ID only in the later repository-level screening table. `total_count` is context, not the bounded-frame size or an eligibility count. GitHub documents `sort=updated`, `order=desc`, `per_page` up to 100, `page`, and the `Link` header ([search endpoint](https://docs.github.com/en/rest/search/search), [pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)). This is repository search, not code search or a screen for metric definitions. No README or source-content endpoint is part of the acquisition.

All 30, 30, and 5 entries had distinct numeric IDs **within their respective pages**. A repeat `rill metrics` page-one probe at 01:44:09 UTC had the same 5 entries and body digest; that brief agreement is not a stability guarantee. Earlier probes with `per_page=2`, pages 1 and 2, used default best-match sorting: all six requests returned HTTP 200 and `incomplete_results=false`. They are separate exploratory requests and supply no rows to the fixed frame.

For HEAD feasibility, `GET /repos/{owner}/{repo}/git/ref/heads/{default_branch}` returned HTTP 200, `object.type=commit`, and a 40-character hexadecimal `object.sha` for the first result of each earlier best-match query. A further probe of the first **fixed-parameter** `rill metrics` result (numeric repository ID `1319197496`) returned `refs/heads/main`, commit SHA `be540b5206a5f6f839e72d9fb30c30bb6cd8870d`, with server `Date` 2026-09-28 01:44:13 UTC. This is an example of the metadata method, not a pinned project in a frozen frame. GitHub documents that the single-ref endpoint returns the ref's commit object and accepts unauthenticated public requests ([Git refs](https://docs.github.com/en/rest/git/refs)).

**Exploratory rate-limit diagnostics only:** the observed search rate-limit header was `10` requests per minute, and the ref probe reported an unauthenticated core limit of `60` requests per hour. These headers and their remaining counts are not part of a later committed acquisition. GitHub documents those unauthenticated limits; they are shared by originating IP and may vary in remaining allowance ([search API](https://docs.github.com/en/rest/search/search), [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). The three exploratory fixed pages contained **65 result occurrences before cross-query deduplication**; a later attempt may have a different count. If its HEAD capture reaches a limit, persist the incomplete attempt and resume pending refs after the returned reset time, recording the extended acquisition interval rather than dropping or silently replacing results.

## Procedure for the later committed manifest

1. Before the run, assign a dated attempt ID and state the three URLs above, API version, page bound, result-order convention, and failure gates below. Fetch each fixed page once in the declared query order. Capture UTC request start/end, the server `Date`, status, final URL/redirects, `Link`, `ETag`, GitHub request ID, and rate-limit headers. A retry after a transient failure starts a **new whole three-query attempt**; never splice pages from different attempts.
2. Store **unaltered raw response bytes** and response headers for each query under the attempt ID. Compute SHA-256 over the raw body bytes and separately over the saved headers. Retain `total_count`, `incomplete_results`, item count, original array index/rank, numeric ID, URL, normalized `owner/repo`, `default_branch`, public/fork/template/mirror flags when supplied, and `created_at`, `updated_at`, `pushed_at`. Store parsed rank rows as a derivative with its own digest; do not replace the raw response with reformatted JSON. Put the attempt ID, exact request target, per-request timestamps, hashes, response sizes, error records, and all rank rows in a versioned manifest, then hash that manifest. These are instructions for a later run; **no such files were created by this audit**.
3. For each distinct numeric repository ID, use the default branch reported in its saved search row and request `GET /repos/{owner}/{repo}/git/ref/heads/{branch}`. Save each raw ref response and headers, request/server times, URL/redirect, `ref`, `object.type`, and full `object.sha`, with individual SHA-256 digests. Require a commit object, exact requested branch ref, and a valid full SHA. Check identity on redirects/renames through repository metadata if needed; retain the original ranked name and numeric ID. Record `404`, `409`, deletion, empty/default-branch changes, and rate limits explicitly. A recorded SHA pins subsequent source inspection to that commit; `updated_at` and `pushed_at` are not substitutes for a commit ID. HEAD may move between the search and ref calls, so report both times without calling it one simultaneous snapshot.
4. Complete the acquisition and hash the immutable search-result manifest **before any held-out source inspection**. If all pages pass but a repository has become unavailable or has no ref, keep its ranked row and explicit unavailability reason; do not invent a SHA or treat it as an eligible pinned project. An accessible repository with an unresolved HEAD needs resolution before it can be admitted. Version and hash later eligibility and selection tables separately, as the evaluation contract requires.

**Failure gates:** HTTP failure, malformed/truncated body, missing page, `incomplete_results=true`, absent response time, unexpected item count for the page bound, duplicate IDs within a page, or missing original order means the attempt is **not** a complete bounded frame. Preserve failure diagnostics and start a new dated attempt rather than claiming a freeze. Record any rate-limited or inaccessible ref and resolve or classify it before source screening. The three pages are the complete **predeclared bound**, even though the first two queries had more matches. The REST search result is a moving index; a stored rank array is an observed acquisition, not a guarantee that another client can regenerate identical ranks later.

## Derivative exclusion and later screening

Before eligibility decisions, compile a numeric-ID/full-name exclusion ledger for the previously inspected Jaffle, Sidemantic, GTM, and Rill development projects from existing development records, without opening any candidate source. Keep every ranked appearance in the manifest. In a separate, versioned decision table, mark direct matches and demonstrable forks, mirrors, template descendants, shared seeds/datasets, or related commit families as development derivatives. Use public repository metadata (`fork`, parent/source IDs from repository metadata where applicable, `mirror_url`, template metadata) and documented provenance; leave uncertain family relationships explicitly pending until a predeclared source-eligibility stage, before labels or predictions. Do not guess ancestry from a similar name alone. Apply the contract's accessible-public-Git and versioned-definition rules **after** the manifest exists, record every rejection and reason, and advance in the prescribed hash order if a later source screen rejects a candidate. A missing positive, unsupported syntax, or failed build is not an exclusion criterion. No positives or project code were inspected in this audit.
