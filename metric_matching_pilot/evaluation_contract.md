# Evaluation and annotation contract (prospective audit)

Date: 2026-09-27. This audits `heldout_sampling_protocol.md` and the development taxonomy without inspecting any new heldout project code. It is an implementation contract for a future evaluation, not a completed benchmark or a replacement for the earlier protocol. The inspected Jaffle, Sidemantic, GTM, and Rill cases, synthetic fixtures, author decisions, and separate AI reviews remain development evidence, not independent human gold labels. Resolve and timestamp the decisions below **before** sampling new test code or seeing system outputs; retain the original protocol and a change log.

## 1. Freeze the frame before opening heldout code

1. Save an immutable, dated search-result manifest *first*. Include exact query text and API/search surface, UTC search time, sort and pagination parameters, every result and its original rank on every page in the bounded search frame, raw response or content digest, inaccessible/truncated pages and rate limits, repository URL and normalized `owner/repo`, default branch and HEAD SHA at the snapshot, and the method used to obtain that SHA without reading source. Record the number of pages searched in advance, rather than stopping when attractive repositories appear. Give the manifest and later eligibility/selection tables their own hashes and versions. **No new heldout repository source should be opened until this manifest exists.** A mere list of selected repositories is insufficient.
2. Apply the draft's three query families (`dbt metric`, `dbt semantic model`, `rill metrics`), accessible-public-Git and versioned-definition eligibility rules to the frozen results. Operationalize the source screen before opening code: inventory only declared numeric measures or reproducible aggregate queries, at least two scalar definitions for the pair task, and an accessible adjacent commit for the event task. A project can be eligible for one task and lack the other. Local rows and successful builds are not prerequisites to inspectable source definitions. Record every rejection, unavailable repository, fork/mirror, shared dataset, submodule, and independence decision with a reason. Exclude all earlier inspected projects and their derivatives. Eligibility must not depend on finding an equivalence, a behavior change, a successful build, or a matcher-supported syntax. If code inspection changes eligibility, append the decision and evidence before looking at pair labels or predictions; advance to the next hashed eligible repository. Failed builds and unsupported definitions remain coverage outcomes, not quiet exclusions.
3. Pin each repository at the manifest SHA, including submodule and dependency SHAs when material; do not choose a favorable historical commit after inspection. Apply the existing lexicographic SHA-256 `owner/repo@commit` rule to select four unrelated **pair-eligible** projects. Publish the whole eligible order and any replacement steps. Among these four, record which also support an adjacent-commit event task; do not replace a pair project just because no metric change occurs. The draft's 12-month / 100-most-recent-commits rule then defines the adjacent parent-child event window; record merge-parent choice, time boundary, repository with fewer commits, and all enumerated metric IDs before sampling events. A metric's stable ID, rename links, source location, and extraction failure should be recorded so that missing/unsupported events do not disappear.
4. Precompute the *pair sampling frame*: all eligible scalar definitions at the pinned version and all unordered within-project pairs, with overlap and inclusion rules for lexical, shared-lineage, and hash-random strata. Freeze the lexical score/tokenization, lineage implementation, hash seed and ordering, stratum quotas, deduplication order, and per-pair inclusion probability if a prevalence estimate is intended. Freeze changed/unchanged event strata and rename handling before drawing the draft's up-to-10 events per project; include unchanged controls. The draft's up-to-25 pairs and up-to-10 events per project are an audit/classification sample; they cannot establish retrieval recall by themselves. Keep supplemental discovered positives outside the test denominator. Report actual quotas and class counts even when positives are absent; do not top up based on labels.

**Open design choices to lock before that manifest:** search date and page limit; whether executable aggregate queries outside declared metric YAML count as definitions (and the exact extractor); one metric versus multiple time/dimension variants as separate IDs; how to handle forks, templates, and shared seeds; tie breaking and merge-parent policy; and whether cross-project retrieval is in scope. This contract's primary retrieval universe is **within one pinned project/version**. Across-version linking and change detection are separate tasks. If cross-project matching is claimed, define and exhaustively judge a separate cross-project universe before testing it.

## 2. What a judgment means

The primary unit is one **numeric scalar output** (possibly a grouped scalar) from each of two identified definitions. Record version SHA, measure/expression and source location, native grain, compared scalar field, grouping keys, time key and window, eligible population, snapshot/business state, unit/currency, filters, and value semantics. An alias or equality of one field does not license a claim that the *whole row* is equivalent. A whole-row claim is a separately marked unit requiring enumerated projected fields, key uniqueness and row multiplicity, join behavior, and NULL/absent-row handling; do not mix it into scalar pair scores. SQL/dbt source, semantic-layer declarations, compiled output, row checks, and owner assertions are distinct evidence types. Cite immutable file/line or artifact/commit references and record exactly what was executed. A finite row reconciliation supports an observation, not a proof over all valid inputs or native-engine portability.

Store two independent axes for each pair judgment. The primary relationship is at the recorded comparison scope. A cross-grain primary label must cite an established transformation to *that same scope*; a relationship at an alternate grain, time or population is a separate conditional claim.

| Axis | Allowed values | Decision rule |
| --- | --- | --- |
| Primary relationship at the recorded comparison scope | `direct_equivalent`, `cross_grain_equivalent`, `temporal_or_scope_variant`, `related`, `conflicting_definition`, `non_match`, or `null` | `null` means evidence cannot decide; it is never a seventh relationship. Direct equivalence requires supported equality at the same grain/time/population/unit and value rules. Cross-grain equivalence requires a specified valid map and aggregation at this target scope. |
| Evidence status | `sufficient`, `needs_review` | `needs_review` names the decisive missing fields, unavailable execution or disputed assumptions; retain a tentative label only as an unscored note. An adjudicated gold relationship requires `sufficient`. |

`temporal_or_scope_variant` requires the same identified conceptual quantity with a changed time rule, business state, filter, population, or hierarchy; disjoint slices of the same additive measure qualify. `related` covers linked but non-substitutable quantities without an established variant rule (including linked counts of different entities). `conflicting_definition` needs evidence that the same asserted identity/name is used for incompatible meanings **without** a coherent scope variant; mere string similarity is insufficient. `non_match` requires source-supported distinct quantities with no defined meaningful link in the available project context, not a universal proof of unrelatedness. If a shared name and changed filter can coherently be explained as a scope variant, choose the variant and record the naming conflict as rationale. Missing lineage, a similar formula over different source populations, or one equal total cannot be converted into equivalence.

**Conditional relation is a second claim, not a replacement for the primary label.** Record the exact transformation and target grain/time/population, its input and output fields, and every prerequisite: aggregation and additivity, hierarchy membership, join keys/type/cardinality and duplicate policy, unassigned source rows, missing groups and `NULL` versus zero, filters and exclusions, period boundaries and timezone, snapshot alignment, units/currency/conversion and rounding, and source-row identity. Give each prerequisite evidence (`verified`, `not_applicable` with reason, `assumed`, `unknown`, `contradicted`) and its source. An established conditional cross-grain gold positive requires every decisive prerequisite verified or demonstrably inapplicable for the declared domain; assumptions/unknowns force an unresolved claim, and a contradiction refutes it. At a different grain or time scope, issue a new unit or conditional claim. For example, equality of daily totals cannot silently imply order-level equality when orders without items yield NULL item sums.

A version event compares one linked scalar definition in an adjacent parent-child commit. Independently record `behavior_preserving`, `behavior_changing`, or `null`, plus `sufficient`/`needs_review`, the affected input domain or counterexample and unaffected domain if known, compiled/source evidence and observed-row evidence separately. An expression difference alone is not proven behavior change; an unchanged expression with changed dependencies is not automatically preserving. If a source-level counterexample establishes changed behavior but no production row is observed, say so. Record developer intent (`intended`, `unintended`, `unknown`) only with owner/issue evidence, separately from behavior. Downstream references establish **potential** consumers; actual changed consumer values or remediation require separate evidence. Link renames explicitly; do not infer a metric's disappearance is behavior preserving.

## 3. Human ground truth and provenance

Two domain-capable **human** annotators independently receive the same pinned, source-linked evidence packet and rubric, recorded by version and digest. Hide system predictions, first-analyst labels, each other's answers, and reconciliation summaries that encode a previous judgment; allow source and reproducible checks. Record each identity under a pseudonym, expertise, timestamp, exact scope, relationship and evidence status, conditional prerequisites, missing evidence, confidence, rationale, evidence references, and time spent. Calibrate the rubric on development cases only. Preserve original submissions unchanged. A third domain-aware human sees both submissions and source to resolve disagreements, including status, transformation, and scope disagreements; record their independent rationale and any additional evidence. For agreements, audit a prespecified subset for rubric drift. If adjudication cannot resolve missing evidence, keep `needs_review` and exclude that unit from scored gold, with counts and reasons. Report raw agreement by axis and class and adjudication frequency; confidence is not a substitute for adjudication. Prior AI reviews and author acceptance cannot satisfy this human requirement.

The companion `annotation_schema.json` validates the core record shape and requires two human judgments plus an explicit finalization: independent agreement or third-person adjudication. It cannot establish annotator independence, identity separation, source truth, or exhaustive coverage; verify those operationally. Keep a separate versioned data dictionary for metric IDs and source artifacts, and retain corrections as append-only revisions.

## 4. Retrieval, classification, and maintenance scoring

**A complete anchor universe for Recall@k.** Set a feasible per-project anchor quota and judgment budget using development-project sizes, then freeze them before heldout inspection. Select anchor metric IDs by a fixed hash from each selected project, independently of rankers and labels. For each anchor, enumerate *every other eligible scalar definition* in that project's pinned version (including extraction failures); have two humans judge every anchor-candidate pair and adjudicate, including apparent negatives outside the sampled lexical/lineage strata. Deduplicate symmetric pairs but preserve each anchor's denominator. Freeze eligible metric IDs, anchor IDs, candidate IDs, exclusions, and universe cardinalities. Only fully judged anchors with resolved sufficient-status relations enter exact Recall@k. If exhaustive annotation exceeds the budget, reduce the **number of anchors by a predeclared hash rule**; if any selected anchor is unresolved, report it as unscored and show coverage and sensitivity bounds. A top-25 judged pool yields only *judged-pool recall*, clearly named as such, never exact Recall@k. Do not treat unjudged or `needs_review` candidates as negatives.

For `k = 1, 5, 10` (or another preregistered set), report retrieval of adjudicated direct-equivalent positives and conditional cross-grain positives in **separate** denominators; state whether a conditional positive requires a transform proposal from retrieval or only candidate discovery. Every candidate's status for that *specific target* must be resolved: a sufficient native `related` label does not resolve an unknown conditional cross-grain claim. If retrieval claims variants, conflicts or change links too, define and report those target sets separately. Report micro positive-pair recall, per-project and macro-over-positive-anchor recall, number of zero-positive anchors, universe sizes and extraction coverage. Zero-positive anchors have no per-anchor recall denominator. Apply `min(k, |universe|)` and publish missing/failed rankings as misses, not exclusions. With four projects, show project-level results and intervals or leave-one-project-out sensitivity rather than presenting pairwise independence as a precision estimate. Do not report exact recall if any decisive pair in the evaluated universe remains unresolved.

For classification, use the **same fixed adjudicated candidate pairs** from the draft's sampled strata for every classifier, independent of their retrieval. Report a confusion table across the six relations, sufficient-status coverage, conditional-claim correctness and prerequisite failures, status/abstention behavior, and separate event behavior classes. Stratified pair results are conditional on this sampling scheme; unweighted accuracy or observed class prevalence must not be generalized to all project pairs. A prevalence estimate needs computable inclusion probabilities and a defensible weighted design. Report source subset/extraction coverage and skipped definitions in every stage. End-to-end results combine each retriever and classifier on the frozen universe, count unretrieved positives as misses, and distinguish alert, conditional suggestion, and abstention.

An **unsafe equivalence assertion** is an unqualified direct/cross-grain output contradicted by adjudicated native-scope gold, or a conditional equivalence output that omits or falsely asserts a necessary prerequisite. Count unsafe assertions per issued equivalence, per candidate opportunity, and by project; keep unsupported/unknown-gold cases in a separate audit tally rather than calling them true or false. Report false negatives, abstention/coverage and risk at a fixed alert or human-review budget. Pair these with runtime, tokens/API cost if applicable, source files inspected, reviewer minutes, and adjudication minutes. Measure review effort in a blinded, randomized reviewer study: comparable heldout tasks with the same evidence and time budget, assignment of baseline versus proposed explanation by anchor/project, counterbalanced order, qualified reviewers distinct from gold adjudicators, logs of opened evidence and edits, and post-review decisions compared with concealed gold. Treat measured consumer remediation and verified incidents as distinct endpoints, not inferred from a dependency path.

## 5. Fair comparators and claim test

Freeze each method's version, thresholds, prompts, token budget, candidate limit, compute budget, and tuning on **development projects only**. At minimum compare exact/normalized names and lexical similarities, normalized SQL/expression and source-lineage matching, a practical constraint-aware implementation for grain/filters/joins/time, and a context-matched LLM if feasible. Publish the actual input-access matrix using these sets:

| Input set | Content | Eligible comparisons |
| --- | --- | --- |
| `I0` names | Same enumerated metric IDs, names, aliases and pinned version IDs | Exact/name/token/Soundex/Jaro-Winkler/Jaccard retrieval; a limited-input comparator to full context. |
| `I1` source context | `I0` plus the *same* version-pinned SQL/YAML, compiled metadata where available, field/source lineage, documented grain/time/filter/unit metadata, and equal executable-check budget | SQL/lineage, constraint-aware, proposed, and full-context LLM retrieval or classification. Do not give any method gold cards, adjudicated prerequisites or an exclusive manually curated field. |
| `I2` version context | `I1` at parent and child commits plus the same diff, dependency graph, and declared consumers | Maintenance/change comparators and proposed method; verify consumer effects separately. |

All retrieval methods see the same universe at the chosen set. All classifiers see the same fixed candidate set, source packet and output schema within each full-context comparison. If a method cannot parse a field, charge the failure to coverage; report limited-input results separately. Manually supplied complete cards and oracle gold prerequisites belong in a separately named upper-bound experiment. Measure full pipelines at matched review budget and compare classifiers with shared candidates; do not attribute retrieval failures to classification. Ablate version context and conditional grain/NULL/time evidence to test their incremental contribution.

The proposed novelty is a **version-aware, evidence-backed conditional maintenance decision** that reduces unsafe equivalences and actionable-review work beyond credible SQL/lineage and constraint-aware alternatives. Predeclare a practically meaningful margin and primary operating point on development data before opening test results. A robust heldout result in which stronger comparators match the false-equivalence/recall/review-effort frontier, or ablations of version and conditional evidence leave decisions and reviewer outcomes materially unchanged, defeats a claimed incremental matcher benefit. Few positives, unresolved gold, or wide project-level uncertainty make the claim untested rather than supported. If source-linked potential consumers do not predict verified downstream effects, narrow the maintenance-impact claim. Do not infer success from constructed controls or a single translating engine.

## 6. Private industrial sample, if authorized

Obtain the data custodian's permission and applicable institutional/ethics review before collection. Use a documented selection frame for versioned definitions, change tickets, owner decisions, and downstream maintenance actions across teams and periods; retain refusals and missing-history counts. An owner assertion is evidence of intended semantics, not automatically independent gold. Separate discovery, two human labels, and adjudication where possible; document reviewer roles and conflicts. Collect the minimum necessary definition metadata, aggregate checks, and decision/effort logs; exclude raw customer records, credentials, personal data and proprietary code from the public artifact. Pseudonyms and SQL snippets may still reveal commercial information: approved redaction, access control, encrypted storage, retention/deletion rules, and release review are required. Do not transmit private definitions to external LLM services without explicit approval. Publish only approved aggregate counts, sanitized examples, and a reproducible public protocol. Evaluate throughput in definitions, candidate pairs, versions and reviewer time; underlying petabyte volume alone is not evidence of matching scale or benefit. Disclose convenience sampling, absent owners, and inability to release private gold.

## 7. Failure modes to disclose before any result

- Search ranking, moving HEADs, hidden pages, permissive eligibility, and post hoc project replacement can bias the sample even if a hash is used.
- Pair-stratum quotas oversample similar negatives and cannot reveal every positive; an incomplete anchor pool invalidates exact Recall@k.
- Source syntax support, absent compiled artifacts, missing runtime rows, cross-engine differences, unknown hierarchy cardinality, changed upstream dependencies, and NULL semantics can convert apparent equivalence into `needs_review` or a counterexample. Report these as coverage and evidence gaps.
- Relationship labels are scope-dependent and can coexist with a verified conditional relation; collapsing them hides false equivalences. Reviewer access to system answers, earlier selected development labels, or suggested transformations can contaminate gold.
- Rare natural positives, many variants, four heterogeneous projects, and correlated pairs/commits may make per-class estimates unstable. Report the observed denominators and limit the claim rather than manufacturing positives or claiming industrial prevalence.
