Key facts: These metrics differ in three fundamental ways:

  1. Different grain: Customer-level vs order-level. The customers table pre-aggregates SUM(orders.subtotal) per customer.
  2. Different values: lifetime_spend_pretax = SUM(subtotal) = 637,444 while order_total = SUM(subtotal + tax_paid) = 671,425. The difference is the total tax: 33,981.
  3. Different time dimension: first_ordered_at (customer's first order date) vs ordered_at (each order's date). Monthly breakdowns are completely incomparable.

My label: related — both derive from order subtotals, but differ in tax inclusion, grain, and time dimension. Too many differences for cross_grain_equivalent (which requires aligned inputs, time, and population). Evidence status: sufficient.

Rubric stress test: This pair is the most interesting for testing the rubric. A reviewer might be tempted to call it cross_grain_equivalent (customer rolls up from orders) or temporal_or_scope_variant (pre-tax vs post-tax). The tax difference alone rules out equivalence, and the different time dimensions rule out a simple grain rollup. The rubric should explicitly address pairs with multiple simultaneous differences.

3. Study Design Evaluation

3.1 Strengths

Rigorous reproducibility controls. Pinned commit SHA, exact dependency versions, SHA-256 integrity checks on worksheets, and read-only protocol ensure all reviewers see identical artifacts. This is above-average for inter-rater reliability studies.
Clear separation of roles. The Reviewer A / Reviewer B / Adjudicator C design with anonymous codes and no live discussions follows best practices for annotation studies.
Well-structured rubric. Six labels cover the expected relationship space well, from exact equivalence through conflict to non-match. The tie-breaking rules (most specific label, equal-only-at-some-scopes caveat) reduce ambiguity.
Honest handling of uncertainty. The needs_review status and "unresolved" adjudication outcome acknowledge that not all pairs have clear answers. This is methodologically mature.

3.2 Concerns

C1: Reviewer A is the paper's first author. This is the study's most significant methodological weakness. While the ADJUDICATOR_GUIDE explicitly instructs the adjudicator to give A's answer "no extra weight," the adjudicator knows which reviewer is the author. This creates unconscious anchoring bias. Standard practice in annotation studies is to use fully blinded codes (e.g., Reviewer 1 and 2 with random assignment), where the adjudicator genuinely does not know which is the author. Recommendation: Either blind the adjudicator to which reviewer is A, or recruit a second independent reviewer (Reviewer C) who is not the author, making the author's labels a separate comparison point.
C2: Only DuckDB is supported. The SETUP.md restricts to DuckDB as the warehouse backend. While this ensures reproducibility, it ties the study's metric behavior to DuckDB's SQL semantics (e.g., type coercion, NULL handling, CASE expression behavior). If the eventual paper claims generalizability to "dbt metrics" broadly, this limitation must be stated. DuckDB's behavior may differ from Snowflake, BigQuery, or Redshift on edge cases.
C3: Sample size and representativeness unknown. Only 3 practice pairs from one project (jaffle-shop) are present. The README promises "held-out packets" from other projects, but these are not yet included. The study's statistical power and generalizability depend entirely on the number and diversity of main-round pairs, which cannot be evaluated from the current materials.
C4: No AI tools restriction is appropriate but limits scalability claims. The study bans AI tools to ensure human judgment is the gold standard. This is correct for establishing the reference dataset, but the paper should explicitly discuss how the protocol scales when applied to large dbt projects with hundreds of metrics, and what the intended downstream use of the labeled dataset is (e.g., training or benchmarking an automated system).
C5: Windows is untested. SETUP.md acknowledges "The Windows steps follow the official tools' documentation but weren't tested by the coordinator." If any reviewer uses Windows, untested setup steps could introduce environment differences or participant frustration. Either test the Windows path or restrict to macOS/Linux.

4. Rubric Evaluation

4.1 Label Definition Issues

R1: cross_grain_equivalent is under-specified. The definition requires "a specified deterministic, valid rollup maps one grain to the other under aligned inputs, time, units, and population, including missing-group and NULL handling." But it doesn't specify: (a) who specifies the rollup — must it be documented in the project, or can the reviewer infer it? (b) What counts as "aligned time" when the two grains use different time dimensions (e.g., first_ordered_at vs ordered_at)? CAL-02 exercises this gap directly.
R2: temporal_or_scope_variant vs related boundary is blurry. The definition says "documented shared measure concept with a changed time rule, filter, state, or population." But what counts as a "shared measure concept"? In CAL-01, revenue and food_revenue share the concept of product price summation but use different measure expressions (SUM(product_price) vs SUM(CASE WHEN ...)). Are they scope variants or related? The inline CASE is effectively a filter, but it's expressed differently from a MetricFlow filter: clause. Clarify whether inline CASE expressions in measure expr count as "filters."
R3: Multiple simultaneous differences are not addressed. The rubric gives rules for picking the most specific label, but doesn't guide reviewers when a pair differs on multiple axes simultaneously (CAL-02: different grain + different values + different time dimension). Should the reviewer pick the "primary" difference? Default to related? The rubric would benefit from a decision tree or hierarchy for multi-axis differences.
