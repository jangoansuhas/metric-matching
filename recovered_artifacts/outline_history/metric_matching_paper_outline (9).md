## Paper at a glance

**Software maintenance problem.** Analytics teams maintain SQL models and semantic metric declarations over time. Two definitions can have similar names but differ in grain, filter, time, business state, or NULL handling. A definition can also change across commits without a corresponding name change. A useful maintenance tool must explain the relationship, identify missing evidence, and avoid unsafe equivalence assertions.

**Primary study objects.** Published numeric dbt Semantic Layer metric declarations and their source SQL at pinned revisions of public repositories. Within-project pairs at one revision form the primary relationship task. SQL aggregate-query output aliases are a separate, broader object kind, not silently interchangeable with metric declarations. Adjacent parent–child commits are a separate, prospective change-analysis task and must not be advertised as a measured drift result unless evaluated. A named measure and a published metric are distinct objects unless a verified binding connects them. The study does not use employer definitions, proprietary findings, or student-record deduplication.

**Paper-one scope decision (September 29).** Finish one public-data Industrial paper on *within-revision* metric relationship decisions and their maintenance failure modes. Compiled provenance, a small number of source-supported decisions, bounded row counterexamples, and a fair strong-baseline comparison are the intended evidence. Across-commit drift has a separate, deferred paper plan; it supplies neither gold labels nor results here. Park cryptographic custody, an unused LLM comparison, and optional evaluation machinery unless a concrete result needs them. A zero-decision method is a diagnostic baseline, not the paper's completed method.

**Claim to test.** Evidence-linked comparison with explicit grain, time, scope, and value-semantics prerequisites may improve maintenance decisions over a **mask-aware** AST/lineage and constraint comparator given the same source context and decision coverage. The two current Jaffle development outputs tie an independently implemented mask-aware AST rule exactly, so this remains an untested hypothesis. A public source-linked failure and coverage study is the alternative contribution if independent human judgments do not show a credible method difference.

## 2. Task definition and relationship taxonomy

**Comparison unit.** One identified numeric scalar output from each of two version-pinned definitions under a declared target grain, population, time window, snapshot/business state, unit, grouping, and value rule. Whole-row equivalence is outside this scalar task unless separately specified and checked.

**Assertion scope.** A label applies to the predeclared compatible request or bounded request family on the pair, including grouping keys and time/dimension support. A general substitution claim covers only the explicitly stated supported family; one valid unequal keyed result refutes a claim that includes that request. An assertion explicitly limited to an ungrouped scalar is not refuted by a month-grouped difference. Unsupported common requests remain unresolved, not negative labels. This rule is prospective for the new cohort and does not retroactively create held-out judgments.

**Primary relationship classes at the stated scope:**

| Class | Decision criterion (verbatim from the distributed practice packet) |
| --- | --- |
| `direct_equivalent` | Same defined output under aligned grain, inputs, time, units, and population, without a grain-changing transform. |
| `cross_grain_equivalent` | A specified deterministic, valid rollup maps one grain to the other under aligned inputs, time, units, and population, including missing-group and NULL handling. |
| `temporal_or_scope_variant` | Documented shared measure concept with a changed time rule, filter, state, or population. |
| `conflicting_definition` | The same or materially similar published name is used for incompatible documented meanings. |
| `related` | Documented semantic connection, but the defined outputs do not meet a more specific label. |
| `non_match` | No supported semantic relationship for the compared outputs. |

**Unresolved practice boundaries.** CAL-02 tests scope versus distinct quantity; CAL-03 tests semantic connection and missing evidence. A development build verifies CAL-03's technical cross-model binding, but no blind third-person adjudication has settled the relationship. The existing practice packet and any prospective rubric amendment must remain distinct. Move the full worksheet history, amended wording and constructed controls to the annotation supplement; none establishes natural held-out gold.

**Evidence axis.** Use `needs_review` when a decisive fact is missing; leave the label blank if needed and name the missing fact. A proposed immaterial-gap amendment was **not** applied to the original practice worksheets. For conditional relations, state the transform and each prerequisite's status. Full rubric and worksheet provenance remain in the annotation supplement.

**Prospective across-version task.** If resources allow, link one scalar between adjacent commits by a source-supported ID or rename. Distinguish behavior-preserving, behavior-changing, and unresolved changes. Record a source-level affected input domain or counterexample and any finite observed-row evidence separately. Dependencies and potential consumers do not establish observed downstream impact. This task requires its own gold, baseline, and results before the paper can claim drift detection.

## 3. Related work and novelty test

- [Valentine: Evaluating Matching Techniques for Dataset Discovery](https://arxiv.org/abs/2010.07386) supplies schema-matching scenarios, benchmarks, and evaluation practices. The [PVLDB Valentine demonstration](https://www.vldb.org/pvldb/vol14/p2871-koutras.pdf) is a separate demo, not the main empirical paper.
- [ConStruM](https://arxiv.org/abs/2601.20482) demonstrates structure-guided context for LLM schema matching. [Constraint-Guided Enterprise Data Mapping](https://arxiv.org/abs/2608.24218) combines constraints, ranking, and LLM disambiguation. Context packing, constraints, abstention, and an LLM are therefore prior ideas.
- [GEqO: ML-Accelerated Semantic Equivalence Detection](https://arxiv.org/abs/2401.01280) studies scalable equivalence of executable computations. AST/lineage tools supply a practical strong source-context comparator. Business-scoped metric relationships and maintenance effects still require separate evaluation.
- [SPES](https://arxiv.org/abs/2004.00481) proves SQL query equivalence under bag semantics; [SQLSolver](https://haoran-ding.github.io/assets/pdf/sqlsolver.pdf) handles aggregation-related equivalence proofs. These tools set a stronger prior-work boundary for executable SQL than string similarity; applicability to compiled metric queries and tool coverage must be measured rather than assumed.
- [Qiu, Li, and Su (ESEC/FSE 2013)](https://www.cs.ucdavis.edu/~su/publications/fse13-db-study.pdf) empirically study co-evolution of database schemas and application code. This motivates maintenance context but does not itself evaluate the present within-revision metric relationship task. The arXiv identifiers and titles for Valentine, ConStruM, Constraint-Guided Enterprise Data Mapping, and GEqO were checked against their source records; the review here is still selective, not a completed systematic literature search.
- **Falsifiable hypothesis.** Explicit reconciliation prerequisites may reduce unsafe equivalence assertions on the same I1 pairs and source evidence versus the strongest AST/lineage and constraint-aware comparator. Only `direct_equivalent` and `cross_grain_equivalent` assertions can count as unsafe equivalence assertions. The authority is the independent human adjudicated reference with source-linked evidence: count as unsafe when it rejects asserted equivalence at the stated scope, including through a contradicted required prerequisite. Put undecidable/unknown prerequisites in a separate unsupported category, not silently among proven errors.
- **Paired comparison.** For decision-only methods without confidence rankings, use the **intersection of pairs both methods decide**. The primary safety outcome is each method's **unsafe equivalence assertions divided by the same number of common decided pairs**. Separately report each method's equivalence assertion count and its unsafe assertions divided by its own equivalence assertions (undefined when it issues none), plus decisions unique to each method. This keeps the primary denominator matched while showing whether one method simply asserts equivalence less often. Do not invent a selective-risk curve. If comparable calibrated scores exist, freeze a ranking/tie rule before test data and report additional per-project risk at common top-k decision counts.
- **Inference boundary.** The small feasibility sample supports descriptive counts and project-aware uncertainty, not a confirmatory superiority claim. Any future confirmatory test needs a separately justified sample-size and power plan before outcomes. If there are no decisions, adjudicated cases, or equivalence assertions, the corresponding comparison is not estimable. If the strong baseline ties, narrow the contribution to a substantial grounded failure analysis or benchmark rather than claiming a detector win.

## 4. Method: versioned, evidence-linked decisions

1. **Inventory.** Enumerate all eligible numeric metric declarations at a pinned revision, retaining unsupported and unknown numeric eligibility. Keep declared measures separate from exposed metrics; record source positions, stable IDs, and extraction failures.
2. **Provenance.** Link each declaration to its referenced measure, model, compiled scalar expression, field owners, dependencies, and build revision only when each link is verified. On the already inspected development checkout, reproduce `dbt parse` and a MetricFlow metric SQL generation (`mf query --explain` for self-hosted dbt v1, or an appropriate `--compile` path) in an isolated, same-commit build; record dependency lock, adapter, invocation, artifact hashes, and any warehouse-connection requirement. Parsing a semantic manifest or finding a same-named measure is not proof of the executable metric expression; a compiled model file is not by itself a compiled metric query. Report missing links explicitly.
3. **Signature.** Record name/aliases, expression, source lineage, native and target grains, grouping, population/filter, business state/snapshot, time semantics, units/conversion, NULL/absent-row and rounding behavior, plus immutable evidence references.
4. **Candidate retrieval.** Rank within-project pairs at a pinned version. Keep across-version linkage as a separate task. Use the complete enumerated ID frame, including ranking failures, for each method.
5. **Decision.** Compare typed signatures; emit a scoped relationship hypothesis, supporting source lines, an explicit transform where justified, and named missing prerequisites. Abstain when source binding, additivity, joins, or value semantics remain unknown. Add version-diff classification only in the separately evaluated change task.
6. **Consumer context.** Record source-linked potential downstream dependencies. Assert measured consumer changes or maintenance actions only if separately observed.

## 8. Discussion, validity, and ethics

Discuss when source-only maintenance signals are useful; when precise relation claims require compiled metric queries, runtime data, or domain-owner evidence; and when abstention is the safe output. Address public-project selection bias, repository dependence, limited numeric eligibility, Jinja/macros/CTEs/windows, changed dependencies, sparse natural positives, annotator agreement and conflict, and finite-row/engine portability. In the Jaffle development build, `revenue_growth_mom` requires a `metric_time` grouping because of its one-month input offset; an ungrouped scalar query is undefined. Ungrouped `cumulative_revenue` and `revenue` produce the same SQL apart from the output alias, so that query alone cannot distinguish their cumulative versus simple time semantics. Treat grouping and time grain as part of the comparison scope, and test time-aware queries before making broader relationship claims. These are development compiler observations, not adjudicated pair labels. A public repository can be industrially relevant without claiming it is a private enterprise deployment. Use only publicly releasable artifacts and check licenses and source links.
